# 产品原型绘制复刻

本技能根据输入的页面资料（网页链接、截图图片、页面分析结果、产品档案文档或功能清单文档），输出结构完整、可以直接用于开发实现的页面原型说明文档。

---

## 一、何时触发本 Skill

### 触发前提（必须满足，缺一不可）

1. 用户**明确要求**输出"原型说明 / 原型文档 / mockup / 页面还原 / 页面布局说明"
2. 用户提供了至少一种素材（链接、截图、分析结果、PRD、功能清单），**或** 明确表示"按你的理解假设生成"
3. 用户的真实意图是**得到一份原型文档**，而非元问询（"这句话会触发吗"、"skill 怎么用"）

### 反例（不触发，必须让位给其它能力）

| 用户意图 | 应让位给 |
| --- | --- |
| "列功能点 / 写 user story / 拆 epic / 拆功能清单" | feature-breakdown 或人工 |
| "画流程图 / 时序图 / 状态机图" | 通用绘图能力 |
| "评估 ROI / 选方案 / 排优先级 / 写产品方案" | 通用分析能力 |
| "生成代码 / 写前后端 / 把原型做成可运行" | development-implementation |
| "写测试用例 / Bug 清单 / 测试报告" | frontend-backend-testing |
| 元问询（"这句话会触发吗"、"什么时候用这个 skill"） | 直接回答，不调用 skill |
| 仅上传无关图片（猫照、风景照、不带 UI 的图） | 反问澄清，不调用 skill |

### 触发置信度分级

- **高置信**：触发词命中 ✓ + 提供素材 ✓ + 意图明确 ✓ → 直接执行
- **中置信**：触发词命中 ✓ + 素材不足 → 先 AskUserQuestion 询问需要哪种素材
- **低置信**：仅关键词命中、整句是 meta 问询 → 不触发，正常回答

## 二、技能使用场景

适用场景（满足任一即可）：

1. PRD/产品档案 + 视觉稿，需输出标准化原型说明给开发
2. 已有线上页面，需还原一份用于二次开发或竞品分析
3. 仅有截图/链接，需结合通用设计模式推断完整原型
4. 用户接受"参考生成"模式，允许在还原基础上提合理优化建议
5. 页面存在多种状态（加载/空/错误/权限等），需逐一说明

## 三、执行流程

### 第一步：接收并识别页面输入资料

#### 资料类型识别

明确用户提供的资料类型：

- **网页链接**：若 host agent 具备浏览器工具（Chrome / Playwright）则访问；否则降级为"按链接名+常识推断"
- **截图图片**：通过视觉分析识别布局和元素
- **页面分析结果**：结构化数据可直接使用
- **产品档案文档**：包含需求说明和业务定位
- **功能清单文档**：包含模块划分和交互说明

#### 资料完整性评估与处理策略

按下表分档并执行对应策略：

| 档位 | 输入情况 | 输出深度 | 还原度上限 |
| --- | --- | --- | --- |
| 完整 | 链接 + 截图 + 文档（≥2 项视觉素材 + ≥1 项文字素材） | 全 6 块输出 | 90%+ |
| 中等 | 链接或截图二选一 + 部分文档 | 全 6 块，复刻建议块列"待补充清单" | 60%-90% |
| 有限 | 仅链接、或仅截图、或仅文字描述 | 仅核心 3 块（概述 + 布局 + 模块），其它标"待补充" | <60% |
| 零素材但用户坚持 | "按你理解生成" | 全 6 块，**首行强制标⚠️"AI 假设生成，需业务方校对"** | 视为推断 |

**为什么这一步重要**：准确的资料识别和完整性评估决定了后续还原工作的深度与边界。资料越完整，还原度越高；资料越有限，越需要明确标注还原边界。

---

### 第二步：提取页面核心信息

#### 页面目标识别（条件输出）

| 字段 | 有 PRD/产品档案时 | 仅有截图/链接时 | 无法判断时 |
| --- | --- | --- | --- |
| 页面所属产品/业务类型 | 必填 | 标注"⚠️ 无 PRD 输入，业务定位为推断"+ 给推断 | 写"待补充" |
| 页面主要功能定位 | 必填 | 同上 | "待补充" |
| 目标用户群体 | 必填 | 同上 | "待补充" |
| 核心价值主张 | 必填 | 可省略 | "待补充" |

⚠️ **严禁**：仅凭截图就替业务方做"价值主张"等强主观判断而不加推断标注。

#### 布局结构提取

1. **整体布局框架**：页面宽度、Header / Content / Footer / Sidebar
2. **栅格系统识别**：列数、间距、响应式断点
3. **视觉层次结构**：一级（核心）/ 二级（辅助）/ 三级（细节）

**为什么这一步重要**：布局结构是页面的骨骼系统，准确提取布局才能确保后续开发实现的还原度。

---

### 第三步：模块拆解与功能说明

#### 模块分级（避免长页面输出爆字）

| 优先级 | 判定 | 输出深度 |
| --- | --- | --- |
| P0 核心模块 | 主交互入口（搜索框 / 列表 / 表单 / 详情主体） | 完整 8 行表格 |
| P1 次要模块 | 辅助内容（推荐位 / 标签 / 二级筛选） | 3 行简表（名称 / 位置 / 内容） |
| P2 装饰模块 | 分割线 / 装饰图 / 静态横幅 | 一句话带过 |

#### 模块完整信息字段（仅 P0 模块要求）

- 模块名称和唯一标识
- 所在位置和尺寸规格
- 包含的子元素和内容
- 样式特征（颜色、圆角、阴影）
- 状态变体（如有）

#### 模块示例（商品卡片列表，P0 级）

| 属性 | 内容 |
|------|------|
| 模块名称 | 商品卡片列表 |
| 容器规格 | 2 列栅格，间距 16px |
| 单卡片尺寸 | 宽度自适应，高度 160px |
| 卡片结构 | 图片区(60%) + 信息区(40%) |
| 卡片元素 | 商品图、商品名、价格、销量标签 |
| 样式特征 | 圆角 8px，轻微阴影，白色背景 |
| 交互行为 | 点击进入详情、长按弹收藏菜单 |
| 状态变体 | 默认 / 已售罄 / 缺货 / 限购 |

**为什么这一步重要**：模块化拆解是开发实现的基础。清晰的模块划分和分级规格说明可以让开发直接对应编码、缩短沟通成本，同时避免对装饰模块过度描述。

---

### 第三点五步：文案清单（必填）

原型最重要的实现细节就是**文案**。开发拿到模块说明仍不够，必须有一份完整文案清单。

| 位置 | 中文文案 | 英文文案（如需国际化）| 备注 |
| --- | --- | --- | --- |
| 顶部标题 | 商品列表 | Products | 静态 |
| 搜索框占位 | 搜索商品 / 品牌 / 类目 | Search products | 静态 |
| 空数据态 | 还没有任何商品 | No products yet | 含 CTA |
| 加载中 | 加载中… | Loading… | 动效 |
| 加载失败 | 网络异常，点击重试 | Network error, tap to retry | 含 CTA |
| 操作成功 | 已加入购物车 | Added to cart | toast |
| 价格符号 | ￥ | $ | 货币 |

⚠️ **必填规则**：所有按钮、标签、占位符、提示语、错误码翻译、单位符号都要在这里列出。文案缺失等于交付不完整。

**为什么这一步重要**：文案是原型的灵魂。模块说明告诉开发"长什么样"，文案清单告诉开发"写什么字"。两者缺一不可。

---

### 第四步：交互逻辑还原

> **本步是 v1.2 重点强化区**。
> 默认输出风格：**B 编号清单型**（每条交互用 ①②③ 列出九个维度）。
> 若用户明确指定"用 A 表格型 / C 伪代码型 / D 卡片型"，按需切换；其余情况强制用 B。

#### 4.1 交互分类

1. **基础交互**：点击 / 滑动 / 展开收起 / 滚动吸顶 / 拖拽
2. **业务交互**：筛选 / 排序 / 搜索 / 分页 / 下拉刷新 / 加车 / 收藏 / 分享
3. **多步骤交互**：表单流程 / 确认弹窗 / 引导步骤 / 多步支付

#### 4.2 交互三档置信度标注

每条交互前**必须加**置信度标签：

| 标签 | 含义 | 何时使用 |
| --- | --- | --- |
| `[✓ 可见]` | 资料中可直接确认 | 截图明确显示 / 文档明确描述 |
| `[? 推定]` | 基于通用设计模式推定 | 资料未直接显示但行业通用 |
| `[⚠️ 不确定]` | 资料未覆盖且无通用模式 | 必须标出"待业务方确认" |

---

#### 4.3 交互细节九维度清单（核心强制规范）

**每条交互必须按这 9 个维度逐条列出**，缺哪条标 `[N/A]` 并说明原因，**不得整条省略**：

| 维度 | 编号 | 必答内容 |
| --- | --- | --- |
| ① 触发条件 | trigger | 鼠标 / 键盘 / 触屏 / 自动；具体手势：click / tap / dblclick / longpress / swipe / scroll / Enter / Space / Esc |
| ② 即时反馈 | feedback | <100ms 反馈：按下态 / 涟漪 / 触觉震动 / 焦点环 |
| ③ 处理表现 | processing | loading 类型（骨架 / 旋转 / 进度条）+ 持续时长阈值 + 占位策略 |
| ④ 成功状态 | success | toast 内容 + 停留时长 / 跳转目标 / 内联变化 / 撤销机制 |
| ⑤ 失败异常 | error | 至少覆盖 5 路：网络断 / 接口超时 / 鉴权过期 / 业务校验失败 / 重复点击 |
| ⑥ 边界处理 | boundary | 极值 / 空 / 满 / 重复 / 误触 / 防抖窗口 |
| ⑦ 动效参数 | motion | duration + easing + delay 三件套（数字必填，可推定） |
| ⑧ 无障碍 | a11y | aria-label / 触摸目标尺寸 / 键盘可达 / 焦点顺序 / 对比度 |
| ⑨ 性能预算 | perf | 防抖 / 节流 / 乐观更新 / 帧率要求 / 是否硬件加速 |

**为什么 9 个不能省**：过去交互说明只写 1-3 维度（触发 + 行为 + 边界），开发到了实现层才发现没人定义按下态、动效参数、键盘可达——返工的根因。九维度是"防漏检"清单。

---

#### 4.4 组件态强制矩阵（不可省）

页面里常见的 6 大组件，**每个组件至少要给出对应数量的态**，缺则标 `[N/A] + 理由`：

| 组件 | 必填态 | 最少数量 |
| --- | --- | --- |
| 按钮 | 默认 / hover / 按下 / 禁用 / loading | 5 |
| 输入框 | 默认 / focus / 已填 / 校验失败 / 禁用 | 5 |
| 卡片 / 列表项 | 默认 / hover / 长按 / 选中 | 4 |
| 开关 toggle | 开 / 关 / 切换中 / 禁用 | 4 |
| Tab | 默认 / hover / 激活 / 禁用 / 红点 | 5 |
| 弹窗 / Modal | 进入动画 / 主体 / 退出动画 / 遮罩点击行为 / Esc 行为 | 5 |

**输出格式**：组件态可在「3. 模块说明」表格的"状态变体"字段里展开，也可在「4. 交互说明」中复述要点。两处都要提到，便于开发对照。

---

#### 4.5 动效参数三件套

每个动效**必须给出三个数字**（可推定，但必须有）：

```
动效参数 = duration + easing + delay
```

#### 常见动效推荐基线（用户未指定时按此推定）

| 场景 | duration | easing | delay |
| --- | --- | --- | --- |
| 按下态反馈 | 80-120ms | ease-out | 0 |
| hover 阴影/上浮 | 150ms | ease-out | 0 |
| toast 出现 / 消失 | 200ms 出 + 250ms 消 | ease-out / ease-in | 0 / 2000ms |
| 模态弹窗 | 300ms 进 + 200ms 出 | ease-in-out | 0 |
| 抽屉 sheet | 280ms | spring (stiffness 400) | 0 |
| 列表 stagger | 每项 +30-50ms | ease-out | 累加 |
| 页面切换 | 400ms | ease-in-out | 0 |
| 骨架屏闪烁 | 1500ms 循环 | ease-in-out | 0 |
| 数字滚动 / 计数 | 800ms | ease-out | 0 |

⚠️ **不得只写"有动画"或"过渡平滑"**，必须三件套全。

---

#### 4.6 分平台交互清单

**[移动端]** 必须覆盖：

- 触屏手势：单击 / 双击 / 长按 / 左滑 / 右滑 / 下拉刷新 / 上滑加载 / 双指捏合 / 双指旋转（如有图片）
- 触觉反馈（haptic）：light / medium / heavy 分别用在哪
- 触摸目标最小尺寸 ≥44×44 pt（iOS）/ ≥48×48 dp（Android）
- 横竖屏切换：是否锁定 / 如何重排
- 键盘弹起：输入框是否自动滚入可视区

**[PC 端]** 必须覆盖：

- 键盘：Tab 焦点环 / Enter 提交 / Esc 关闭 / 方向键导航 / Cmd+K 类全局快捷键
- 鼠标 hover：tooltip 出现/消失 delay；hover 区域是元素本身还是包含 padding
- 右键菜单（如有）
- 滚轮 / 触控板：横向滚动 / 双指 swipe
- 多窗口 / 多 tab：状态同步策略

**[触屏 PC（Surface 类）]** 降级规则：

- 无 hover：用长按代替 / 用 active 态代替 / 默认显示原 hover 内容
- tooltip：改成首次出现后常驻 / 点击 ⓘ 出现

---

#### 4.7 反馈机制三档

| 档位 | 时长 | 形式 | 典型场景 | 必含字段 |
| --- | --- | --- | --- | --- |
| 即时（<100ms） | 0-100ms | 按下态 / 涟漪 / 触觉震动 / 焦点环 | 所有可点击元素 | 视觉变化 + 触觉（移动端） |
| 短暂（1-3s） | 1-3s | toast / snackbar / 角标更新 | 加车成功 / 已复制 / 已收藏 | 文案 + 停留时长 + 撤销时长 |
| 持续（>3s） | 3s+ | 全屏 loading / 进度条 / 步骤指示 / 通知中心 | 上传 / 支付 / 审核 / 后台任务 | 进度展示 + 可取消按钮 + 完成通知 |

⚠️ 所有可点击元素**至少必含"即时反馈"**；状态变更类操作**必含"短暂反馈"**；耗时 >3s 的操作**必含"持续反馈"**。

#### 4.8 边界 / 性能 / 无障碍 checklist

每页都要逐项过这三份清单。**模型若跳过任何一项，必须显式写出 `[N/A]` + 简短理由**。

##### 边界异常（每页必检 ≥8 项）

```
□ 网络断开 → 文案 + 重试 + 排队策略
□ 接口超时 (X 秒后？)
□ 接口 5xx：重试策略（次数？间隔？退避？）
□ 鉴权过期 → 跳登录 + 登录后续接
□ 数据并发冲突 → 后到/版本号/合并
□ 重复提交防御 → 防抖 / 按钮置灰
□ 极值（最大 / 最小 / 0 / null / 负数）
□ 长文本截断（中英文 / 全角 / emoji）
□ 长数字换行（金额、ID）
□ 字段长度上限（输入框 maxLength）
```

##### 性能感知（每页必检 ≥6 项）

```
□ 骨架屏 vs 转圈 vs 进度条 → 选哪种？为什么？
□ 是否乐观更新（先改 UI 再发请求 + 失败回滚）
□ 搜索框防抖窗口（推荐 200-300ms）
□ 滚动节流（推荐 16ms / requestAnimationFrame）
□ 图片懒加载 + LQIP（低质量占位图）
□ 列表虚拟滚动阈值（>100 项？）
□ 60fps 帧率预算 / 是否硬件加速 transform
□ 接口预取（hover 时预拉详情）
```

##### 无障碍（每页最低线 ≥4 项）

```
□ 所有可交互元素带 aria-label / aria-describedby
□ 触摸目标 ≥44×44 pt
□ 颜色对比度 ≥4.5:1（正文）/ ≥3:1（大字 + 图标）
□ 键盘 Tab 可达 + 焦点环可见
□ 表单 label-for / 错误提示 role="alert"
□ 动效尊重 prefers-reduced-motion
```

#### 4.9 完整示例（B 编号清单型）

**示例 1：商品卡片"加入购物车"按钮**

```
[✓ 可见] 4.X 加入购物车按钮

① 触发条件
   - 移动端：tap 按钮区域
   - PC 端：单击 / Enter / Space
   - 触发前置：用户已登录 + 商品库存 >0

② 即时反馈
   - 视觉：按下态 scale(0.96) 80ms
   - 触觉：haptic light（移动端）
   - 焦点环：PC 键盘触发时显示

③ 处理表现
   - 按钮文字 → 旋转图标
   - <2s 内响应：直接进入 ④
   - ≥2s 未响应：升级为持续 loading（按钮内显示进度圈）

④ 成功状态
   - toast "已加入购物车"，停留 2s
   - 顶部购物车角标 +1，spring 缩放动画
   - 撤销操作：toast 内含"撤销"按钮，停留期内可点
   - 撤销时长：5s

⑤ 失败异常（5 路分支）
   - 网络断：toast "网络异常，已暂存，恢复后自动加车"
   - 接口超时（>10s）：toast "请求超时，点击重试"
   - 鉴权过期（401）：跳登录页，登录后自动重发
   - 库存不足：toast "已售罄"，按钮置灰
   - 重复点击：节流 300ms 内忽略后续点击

⑥ 边界处理
   - 已售罄状态：按钮置灰 + 文字改"已售罄" + 不响应点击
   - 连续 3 次失败：按钮禁用 10s + 显示倒计时
   - 限购商品：超过限购数量 toast "每人限购 X 件"

⑦ 动效参数
   - 按下态：150ms · ease-out · 0 delay
   - toast 出现：200ms · ease-out · 0
   - toast 消失：250ms · ease-in · 2000ms delay
   - 角标 spring：stiffness 400, damping 25

⑧ 无障碍
   - aria-label="加入购物车"
   - 触摸目标 ≥48×48
   - 键盘 Enter / Space 可触发
   - Tab 焦点顺序：商品名 → 价格 → 加车按钮
   - prefers-reduced-motion 时关闭 spring 动画

⑨ 性能预算
   - 防抖 300ms（避免连击双发）
   - 乐观更新：先角标 +1，请求失败回滚
   - 帧率 ≥60fps（按下态 transform 走 GPU）
```

### 第五步：状态说明整理

对于具有动态状态的页面，需逐一说明各种状态。

#### 通用状态类型

| 状态类型 | 描述 | 说明要点 |
|----------|------|----------|
| 加载态 | 数据获取过程中 | 骨架屏 / 指示器 / 全屏 loading |
| 空数据态 | 无内容显示 | 空插画 / 提示文案 / 引导操作 |
| 错误态 | 异常情况展示 | 错误提示 / 重试按钮 / 联系支持 |
| 权限态 | 权限限制展示 | 权限说明 / 去开通 / 去登录 |
| 成功态 | 操作成功反馈 | 成功提示 / 自动跳转 / 状态更新 |
| 临界态 | 边界情况展示 | 边界值处理 / 溢出省略 |

#### 状态切换逻辑

```
进入页面 → 鉴权
  ├─ 通过鉴权 → 加载态 → 正常态 / 错误态 / 空数据态
  └─ 未通过   → 权限态（含"去登录 / 去开通"出口 → 通过后回到正常态）

正常态 ↔ 操作 ↔ 加载态 → 成功态 / 错误态
错误态 → 重试 → 加载态
```

**为什么这一步重要**：完整的状态说明是保证体验一致性的关键。开发需要知道在各种情况下如何展示页面，减少用户在意外情况下的困惑。

## 四、注意事项

### 关于还原边界（防捏造）

- 若输入资料不完整，**优先还原核心可见模块**，对于无法确认的部分标注为"待确认"
- 若交互无法完全识别，必须使用 `[✓ 可见]` / `[? 推定]` / `[⚠️ 不确定]` 标签
- **不得为追求完整而捏造不存在的页面逻辑**，常见捏造陷阱：
  - 截图未显示"分页"或"加载更多"，却写了无限滚动
  - 仅一页静态截图，却描述了多步骤表单流程
  - 凭页面名称编造业务定位（如名为"列表页"就说"提升 GMV"）
  - 把通用设计模式当作"本页面具体行为"输出

### 关于优化建议

- 第 6 块开头必须有 `> 以下为建议，由用户决定是否采纳。` 强制声明
- 每条优化建议格式：`[建议] {项目}：{改动原因} + {预期效果}`
- 优化建议不得与还原内容混在一起，必须放在专门小节

### 关于多状态页面

- 在第 5 块"状态说明"中，每个状态独立一个三级小节（### 5.1 加载态、### 5.2 空数据态 ...）
- 状态切换逻辑使用 ASCII 图或编号列表
- 边界情况的处理需逐一列出

### 失败兜底

| 情况 | 处理 |
| --- | --- |
| 输入是无关图片（猫照 / 风景照）| 反问用户："看起来不是 UI 截图，请确认。" 不输出原型 |
| 用户中途要求换风格 | 接受改动，**保持文档结构不变**，只重写涉及部分 |
| 资料完全无法识别 | 输出"⚠️ 无法识别"+ 列出能识别到的部分（如颜色基调、大致区域）+ 反问需要哪种素材 |
| 元问询误触发本 skill | 直接停止，正常回答 |
| 用户要求出代码 | 让位给 development-implementation，告知"本 skill 仅出原型说明" |

### 关于涉密素材

若用户上传明显是内部系统截图（含真实用户名、订单号、内部域名等）：
- 在输出文档首行加 ⚠️"输入资料含敏感信息，建议脱敏后再用于对外文档"
- 输出内容中将敏感字段替换为占位（如 `订单号：****`）
