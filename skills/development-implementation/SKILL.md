# 开发实现 Skill（强制对齐版 v3）

## 概述

本技能负责将功能需求转化为**可直接运行的代码实现**，覆盖前端（Vue/React/H5）、后端（Node/Java/Go）及接口逻辑。

**第一原则——完全对齐提供的材料**：开发必须 100% 依据用户提供的 **原型、PRD、功能清单、系统架构** 进行，不得遗漏清单内功能、不得新增清单外功能、不得偏离既定架构。材料未覆盖或冲突之处按下方"冲突裁决"处理，**禁止凭主观假设填补**。

## 何时触发 / 何时不触发

- **触发**：用户明确要求"实现功能 / 生成代码 / 按 PRD 做开发 / 把某模块实现出来"，并（最好）附有原型、PRD、功能清单或架构。
- **不触发**：(a) 纯调试/定位单个 bug；(b) 代码评审、测试、验收、走查（交给 frontend-backend-testing）；(c) 概念问答（"什么是依赖注入"）；(d) 仅口头一句、无任何材料且无明确实现意图——先用 AskUserQuestion 澄清，不要凭空开写。

## 强制执行流程（按序不可跳）

> 门禁：步骤 0、1 未完成不得进入步骤 4 写代码；步骤 6 未通过不得宣称"已完成"。
> 模板见 `references/templates.md`；完整示例见 `references/examples.md`。

### 步骤 0：材料盘点与缺口拦截（硬门禁）

列出收到的材料，逐类标"已提供/缺失"：功能清单、PRD、原型/UI/.pen、系统架构、字段/数据结构、已有代码（修改场景）。

**关键材料（功能清单 / 架构 / 原型）缺失时，一次性提 1–3 个关键问题后暂停，不得假设开工。** 非关键缺失可继续，但须在交付中列"已知 vs 待补"。

### 步骤 1：材料结构化提取 + 编号（写代码前必做）

拆成带唯一编号的可勾选清单：功能点表 `F-xx`（名称/模块/验收要点）、业务规则表 `R-xx`（触发/逻辑/边界）、页面交互表 `P-xx`（组件/状态：正常·空·加载·错误·禁用/跳转/交互节点）、架构约束（分层/目录/技术栈/命名/接口契约）、字段表（名称/类型/必填/约束/来源）。原型为 .pen 时用 pencil 工具读取后提取，禁止臆测。

### 步骤 1.5：冲突裁决（材料打架时）

按固定优先级裁决，不必每次都问：

- **业务规则 / 逻辑 / 校验 → 以 PRD 为准**。
- **交互、页面、流程范围（做哪些页/哪些功能）→ 以原型为准**。
- 二者在**同一点上直接冲突**、或某点两边都未覆盖 → 标"待确认"并询问，不得自行假设。

裁决结果写入清单，并在交付说明里注明"因 X 与 Y 冲突，按规则取 Z"。

### 步骤 2：建立"需求—实现对齐矩阵"（可追溯）

写代码前先产出矩阵（模板见 references）：每个 F/P/R 编号 → 计划实现位置 → 状态。规则：清单内每项必须在矩阵出现；矩阵中不得有清单外"自创功能"；冲突项标"待确认"。

### 步骤 2.5：范围确认 checkpoint（大项目必做）

当涉及多页面/多模块或工作量较大时，**先把对齐矩阵 + 待确认清单交给用户确认，再进入写代码**，避免理解偏差导致大返工。小改动可跳过。

### 步骤 3：锁定技术栈与项目结构（架构红线）

技术栈、目录、命名、接口契约**严格采用系统架构所规定的**。**架构未提供或不明时询问用户，不得"优先主流技术栈"自行决定**；仅在用户明确授权"你定"时才选型，并在交付中说明方案与理由。

### 步骤 4：按对齐矩阵生成代码（逐项回指）

- 按矩阵逐项实现；每个文件/模块顶部注释回指覆盖的编号（`// 覆盖 F-01, R-03, P-02`）。
- 在 Cowork 中**用文件工具实际落盘项目骨架与代码文件**，而非仅在对话贴片段；大项目按目录组织。
- 优先级：核心业务流程 → 修改 diff（改造场景）→ 接口/路由 → 数据模型/Schema → 基础测试。
- 每模块含必要注释、关键逻辑、错误处理、原型要求的全部状态（空/加载/错误/边界）。
- **反臆造红线**：不实现清单外功能；不省略清单内功能；歧义/缺失不猜测，标"待确认"。

### 步骤 5：生成测试 + 可运行性验证（强制）

- 生成后端接口测试、前端组件/单元测试，覆盖主流程、核心分支及关键规则 R-xx。
- **可运行性验证**：在沙箱中尽力做最小验证——能装依赖则跑 lint / 构建 / 单测；语法层面至少做编译或静态检查。验证通过的注明结果；**无法在沙箱运行的（缺私有依赖、需真实后端等）显式标"未实测，需在你环境验证"，禁止默认声称"可直接运行"**。

### 步骤 6：完工覆盖率门禁自检（不通过不得交付）

回填对齐矩阵，逐条标 已完成/部分/未实现(+原因)，并显式回答：
1. **完整性**：功能清单/原型页面/PRD 规则是否每条覆盖？未覆盖逐条列原因。
2. **一致性**：是否有清单外新增或偏离架构？有则标出说明。
3. **待确认**：所有待确认项汇总待用户决策。

存在"部分/未实现/清单外新增"时不得宣称完成。

### 步骤 7：闭环到验收（建议）

交付后建议用户用 `frontend-backend-testing` skill 对照原型/PRD/功能清单做验收测试，形成"开发 → 自检 → 测试"闭环；若用户同意可直接衔接。

## 输出格式

新增开发：材料盘点 → 结构化清单(F/P/R/架构/字段) → 冲突裁决 → 对齐矩阵 →（大项目）范围确认 → 项目结构 → 接口定义 → 核心代码(已落盘) → 测试 → 可运行性验证 → 覆盖率自检 + 待确认。

修改已有代码：修改范围(文件/行号/方法) → 本次覆盖编号 → 变更 Diff → 测试更新 → 可运行性验证 → 覆盖率自检 + 待确认。

> 模板与三个完整示例（新增 / 修改 / 材料缺失拦截）见 `references/templates.md` 与 `references/examples.md`。
