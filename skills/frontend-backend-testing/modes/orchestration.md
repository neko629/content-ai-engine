# 模式 D · 测试编排

## 适用场景

- 复杂项目（多模块、多角色、多端）
- 需要"先规划再执行"
- 多人/多轮迭代测试
- 时间盒较长，需要拆分批次

## 流程

```
1. 制定测试计划（先不动手测）
   ├─ 测试目标
   ├─ 测试范围分解（按模块/功能/接口/角色）
   ├─ 维度优先级（哪些维度先测、哪些后测）
   ├─ 测试批次划分（每批一个分项深测）
   ├─ 风险评估（哪些是 P0 必测、哪些可省略）
   └─ 时间盒/退出条件
2. 输出"测试计划"给用户确认
3. 用户确认后，逐批进入分项深测（调用 modes/deep-dive.md）
4. 每批结束输出阶段报告
5. 全部完成后输出汇总报告
6. 状态追踪：Bug 状态流转（新建 → 修复 → 验证 → 关闭）
```

## 输入要求

- 必需：项目/功能概览
- 必需：测试目标与时间盒
- 推荐：完整原型 / UI 稿 / 接口文档 / 代码仓库
- 推荐：测试优先级偏好（用户最担心什么）

## 测试计划必含字段

| 字段 | 说明 |
|---|---|
| 测试目标 | 一句话目标 |
| 测试范围 | 涉及模块/页面/接口列表 |
| 范围外 | 显式排除的范围（避免歧义） |
| 维度优先级表 | P0/P1/P2 维度分级 |
| 批次规划 | 第 1 批测什么、第 2 批测什么…… |
| 每批入参 | 每批所需材料 |
| 每批产出 | 每批的 deliverable |
| 风险点 | 已识别的高风险点 |
| 退出条件 | 何时算"测完" |
| 责任分工 | 哪些 Claude 做、哪些用户做 |

## 产出（分阶段）

**阶段 1：测试计划文档**（先给用户确认）

**阶段 2 ~ N：分批测试报告**（每批一份分项深测报告）

**最终阶段：汇总测试报告**
- 整体覆盖度
- Bug 汇总表（按严重度、模块）
- 跨维度问题（多个维度都有问题的模块/功能）
- 上线建议
- 后续迭代建议

## 状态追踪机制

Bug 状态字段：
- **新建**：首次发现
- **已确认**：研发/PM 确认
- **修复中**：研发认领
- **待验证**：研发标记修复
- **已验证**：测试验证修复成功
- **回归 PASS**：回归测试通过
- **关闭**：闭环
- **重开**：修复失效再次出现

## 退出条件

- 测试计划获用户明确确认
- 所有规划批次完成
- 所有 P0 Bug 状态 ≥ "已验证"
- 给出可上线/不可上线的明确结论
- 输出汇总报告
