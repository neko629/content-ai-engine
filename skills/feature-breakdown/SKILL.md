# 功能拆解 Skill

> 技术 ID：`feature-breakdown`　·　版本：`v1.0.0`　·　中文名：功能拆解　·　目标用户：产品 / 运营 / 开发 / 测试

## 概述

此技能负责将需求文档、方案说明或业务描述转化为结构化的功能清单，包括功能点拆解、字段定义、菜单结构和业务规则说明。输出结果需可供产品、设计、开发、测试人员直接使用。

**范围外**：本技能**不输出** API 接口签名/参数文档、状态机时序图、权限矩阵 RBAC 表、单元测试用例、UI 视觉稿。如需上述内容，请使用对应专项技能。

## 执行步骤

### 第一步：分析输入内容

首先识别输入内容包含的关键信息：

- **产品对象**：系统要管理或服务的主体是什么（如订单、商品、用户等）
- **核心业务目标**：用户希望通过此功能达成什么目的
- **使用角色**：哪些角色会使用此系统（用户端角色、管理端角色、运营角色等）
- **核心场景**：主要业务流程和使用场景有哪些
- **交付形式**：Web 端 / H5 / 小程序 / APP（影响菜单深度、字段长度、交互方式；不影响功能拆解结构本身，但会影响字段类型选择如 `image` 大小、`text` 长度上限等）

**缺失信息分级处理**：

- 若缺失「产品对象」或「核心业务目标」之一，**必须先主动提问**，不得自行假设；
- 若仅缺失「使用角色」或「核心场景」的细节，按通用默认补足后继续拆解（用户端默认含「普通用户」、管理端默认含「管理员」），并在对应行的"业务规则"列用 `（待确认）` 标注；
- 仅当用户明确说"先粗拆"或"不用问"时，跳过本规则直接全量主流程拆解。

### 第二步：确定拆解范围

根据用户指定的范围确定拆解维度：

- 若用户指定"用户端"或"管理端"，仅输出对应端的功能
- 若用户未指定，默认输出用户端 + 管理端两端功能
- 若用户指定某一模块，按指定模块范围进行拆解

**端判定细则**（与上述默认规则不冲突时优先适用）：

- 若用户提供的"使用角色"列表**全部为内部运营/管理类**（如客服、商家、商户、运营、财务、管理员），视为仅需"管理端"，跳过双端默认；
- 若同时出现 C 端角色（普通用户、消费者、学员、读者、买家、玩家等），按"用户端 + 管理端"双端输出；
- 若用户角色未列、仅给出系统场景，默认"用户端 + 管理端"双端。

### 第三步：结构化功能拆解

按以下层级结构进行功能拆解：

| 层级 | 说明 |
|------|------|
| 一级功能 | 业务模块/子系统（与菜单一级目录对应） |
| 二级功能 | 功能组/页面模块（与菜单二级目录对应） |
| 三级功能 | 具体功能点（可操作的功能项） |

每个三级功能需要包含：

- 功能名称
- 功能描述（详细说明此功能要做什么）
- 涉及字段（若有）
- 业务规则（若有）
- 适用角色（对应输出表的"适用角色"列）

### 第四步：区分端和角色

功能清单**统一输出为一张表**，端归属通过"适用端"列区分。"适用端"取值约定：

- **用户端**：面向普通用户 / 消费者 / 学员 / 客户等 C 端角色
- **管理端**：面向运营、客服、商家、管理员等内部运营角色
- **系统支撑端**（如适用）：后台数据处理、定时任务、第三方对接等无前台界面的功能

若某端不存在相关功能，对应行直接省略；不需要为每个端单独建一张表。

### 第五步：补充字段和菜单结构

若用户需要字段清单或菜单结构，按以下规则输出：

- 字段必须归属到具体功能或页面下
- 字段包含：字段名称、字段类型、是否必填、字段说明
- 菜单结构必须符合实际后台使用路径

## 输出格式要求

**ALWAYS 使用表格样式输出**。若功能清单中某行的"功能描述"或"业务规则"无法在一行内表达清楚，可在表格下方用 `### 补充说明 - {三级功能名}` 形式追加段落。

|----------|----------|----------|----------|----------|----------|--------|----------|

**字段类型推荐枚举**（输出时统一使用以下值，避免每行写法不一）：

| 类别 | 推荐写法 | 说明 |

| 文本 | string(N) / text / richtext | N 为最大长度，text 为长文本，richtext 为富文本/HTML |
| 数值 | int / bigint / decimal(p,s) | decimal 用于金额、比率等需精确小数 |

```

业务目标：帮助商家高效管理订单处理全流程
使用角色：商家、客服、财务
核心场景：
1. 商家查看订单列表，进行订单审核
2. 客服处理退款退货申请
3. 财务核对订单金额，进行对账
```

```
需要管理用户、管理商品、查看订单报表
```

## 注意事项

### 关于输入内容

- **方案文档、PRD**：优先提取结构化信息，按文档原有逻辑拆解
- **自然语言需求**：识别核心业务流程，转化为结构化功能点
- **页面需求说明**：按页面维度拆解，补充字段和交互规则

### 关于功能拆解原则

- **主流程优先**：在「产品对象」与「核心业务目标」已明确的前提下，若用户对功能范围描述宽泛，优先拆解核心主流程功能，不强行扩展全量功能
- **合理性判断**：若缺少明确流程，可补充通用流程模块（如基础CRUD、状态管理、日志记录），但不添加与业务无关的模块
- **角色明确性**：若角色不明确，默认按常规角色理解（如用户端默认包含"普通用户"角色，管理端默认包含"管理员"角色）

### 关于字段定义

- 字段含义不清晰时，先输出建议字段结构并用**待确认**标记
- 必填字段需明确标注，非必填字段说明默认值
- 涉及敏感字段（如密码、身份证号）需标注加密存储要求

### 关于输出质量

- 功能描述需清晰表达"做什么"而非"怎么做"
- 业务规则需包含触发条件、校验逻辑、数据流转等
- 菜单结构需符合实际后台使用路径，避免层级过深（建议不超过3级）

**"业务规则"列范围**：仅写**触发条件、状态前置/后置约束、字段间校验关系、关键的状态流转**。以下不写入该列：

- SLA / 时效要求 → 写入"补充说明"或独立的 SLA 段落
- 统计维度 / 周期 → 归入字段说明
- 界面行为（如"支持导出 Excel"）→ 归入通用约定，不逐行重复

### 关于主动提问

当输入内容缺少关键信息时，鼓励主动向用户确认以下内容：

- 核心业务目标和主要使用场景
- 涉及的角色及其权限划分
- 需要的端（用户端/管理端/两端都需要）
- 是否需要包含字段清单或菜单结构
- 特定行业或业务类型的特殊要求

### 关于反向触发（何时不该用本技能）

以下场景不应触发本技能，请改用对应专项：

- 仅需补充单个字段定义或调整字段类型 → 字段定义/字典维护类技能
- 仅需输出 UI 视觉稿、原型图、Figma 链接 → UI/原型设计类技能
- 仅需测试用例、Bug 清单、回归矩阵 → 前后端测试类技能
- 仅需 API 接口签名、Swagger / OpenAPI 文档 → 接口文档类技能
- 仅需 SQL 表结构 DDL → 数据库设计类技能
